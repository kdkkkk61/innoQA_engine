# 결함 카드 단위 · merge_key 규칙 (요소별 카드 + 동일 내용 묶기)

> fail/warn 검증 항목 작성 시 카드 granularity 와 묶기 기준을 이 규칙대로 한다.
> 확정: 사용자 지시 2026-07-02. 근거 코드: `core/html_reporter.py` `_render_defect_section()`(merge 그룹핑),
> 각 페이지 `_base.py` `_add(..., merge_key=)`. 적용 예: 특수폴더 sc3f/4m·sc3s/4o.

---

## 1. 3층 원칙

| 층 | 단위 | 규칙 |
|---|---|---|
| 검증 커버리지 | 클래스 전수 | 같은 버그 클래스(오버플로·특수문자·중복 등)는 적용되는 **모든 요소를 트리거** (spot-check 금지) |
| ScanResult(검증 항목) | **요소 × 컨텍스트** | 요소별로 개별 판정·개별 `_add` — 원본위치/대상위치를 한 항목에 뭉치지 않는다 |
| 결함 카드 | **요소** | 같은 요소의 생성(sc3)/수정(sc4) 컨텍스트 항목은 `merge_key` 로 **1장으로 묶는다** (갱신 2026-07-09: 결과가 달라도 묶고, 리포터가 결과를 `[시나리오 3.xx] …`/`[시나리오 4.xx] …` 줄로 분리 표기. **요소끼리·타입끼리 가로 병합 금지** — 허용/거부/예외처리/실행차단은 각자 카드) |

- 뭉치면 안 되는 이유: 한쪽 요소만 이슈인데 카드가 둘 다 문제인 것처럼 보임(이슈 귀속 불가).
- 요소끼리(원본↔대상) 묶지 않는다 — 카드의 단위는 요소다.
- 예외: 기대가 '전부 깨끗'인 스캔(i18n 키 누출 등 leaks 가 필드를 자동 특정하는 것)은 sweep 카드 1장 유지.

## 2. merge_key 규약

```python
# 기본형(갱신 2026-07-09): 클래스::요소 — 같은 요소의 sc3↔sc4 가 결과 달라도 한 카드
merge_key=f"szproc_desc_ovf::{ttype}"             # 클래스::요소(타입)
merge_key=f"path_ovf::{elem}::{st}::{note}"      # (구형) 판정·결과까지 키에 — 같은 결과만 묶던 방식
merge_key="manual_admin_pw_crypto"                # 고정 항목(수동확인 표식 등)은 고정 문자열
```

- 형식: `<검증클래스>::<요소>::<판정>::<결과분류>`. 결과분류(note)는 분기별 **고정 문자열 상수**로
  (예: `"raw 서버 오류 노출 — 클라 길이 가드 부재"`) — 실행마다 변하는 값(개수·메시지 원문)을 넣으면 묶임이 깨진다.
- 생성/수정 미러 양쪽에서 **같은 키 체계**를 쓴다 (sc3s ↔ sc4o).
- 같은 페이지 안에서만 묶임 (카드가 페이지 탭 필터 `data-page-key` 에 걸리므로).

## 3. 라벨 규약 (묶인 카드 제목 dedup)

- 미러 항목의 라벨은 **시나리오 prefix 만 다르고 본문은 동일 문구**로:
  `"sc3s — 원본위치 3000자 오버플로 → 처리"` / `"sc4o — 원본위치 3000자 오버플로 → 처리"`.
  리포터가 prefix 를 벗기고 비교하므로 제목이 하나로 깔끔하게 남는다.
- 라벨이 다르면 제목이 ` · ` 로 join 되어 길어진다 — 의도한 경우가 아니면 문구를 맞출 것.
- **결함 분기의 제목은 결함 중심**(사용자 지시 2026-07-10): "무엇이 안 되는가"를 쓰고,
  발견 경위(테스트 절차·트리거 입력)는 제목에 쓰지 않는다. 경위가 제목이면 경위가 이슈로 읽힌다.
  - ❌ `"3000자 시도 후 정상값 재수정 → 복구"` (3000자가 이슈로 보임)
  - ✅ `"편집 '수정'이 적용 안 됨 — 설명·상태 변경 불가(앱 JS 오류)"`
  - 판정 분기별로 라벨을 조건 분기해도 된다(pass 는 검증 서술형 유지, fail/warn 은 결함 서술형).
    적용 예: 프로세스 sc4i(편집 불능 분기)·sc4g(표시 결함 분기).

## 4. 리포터 동작 (`_render_defect_section` 실측)

- 같은 (페이지, merge_key) 항목 → 결함 카드 1장. 카드 번호는 렌더 시 일련번호라 자동 재부여.
- 시나리오 배지 join: `시나리오 3.19 · 4.15` (뒤 항목은 '시나리오 ' prefix 생략).
- 라벨이 서로 다르면 제목도 ` · ` join.
- **검증 항목 표와 요약 카운트는 각자 유지** — 각 시나리오에서 실제 검증된 기록. 묶임은 결함 카드 목록만.
- 카드 내용(재현/입력/스크린샷)은 그룹의 첫 항목 것 사용. **결과는 전수**: 전부 동일하면 "— N건 동일 결과", 다르면 `[시나리오 …]` 줄단위 분리 표기(갱신 2026-07-09).

## 5. 작성 체크리스트

- [ ] 같은 클래스가 적용될 요소를 전부 나열했는가 (전수)
- [ ] 요소마다 개별 `_add` 인가 (한 항목에 dict 로 뭉치지 않았는가)
- [ ] 판정 분기의 note 가 고정 문자열 상수인가
- [ ] merge_key 에 요소명이 들어갔는가 / 미러(sc3↔sc4)와 키 체계·라벨 본문이 같은가
- [ ] highlight 는 해당 요소의 필드/행인가 (→ `issue-screenshot-rules.md`)

## 6. 저장값 3점 대조 (수정 검증의 기본형)

수정 저장 후 값은 **세 지점**에서 대조한다 — 표시 계층과 저장 계층이 따로 틀어질 수 있기 때문
(예: 리스트엔 '활성'으로 남는데 재오픈하면 '비활성' = 리스트 갱신 버그 / 둘 다 원래값 = 저장 버그. 재오픈만 보면 전자를 놓친다):

1. **입력값** — 무엇을 저장했는가
2. **리스트 표시값** — 행/셀에 반영됐는가 (`folder_row_values`, `_row_locator(...).locator("td")`)
3. **재오픈 로드값** — 다시 열면 그 값으로 로드되는가 (`input_value`/`is_checked`)

적용 예: sc4b(템플릿 상태 — 리스트 상태열 + 재오픈 radio), sc4q(폴더 항목 상태 — 행값 + 재오픈 radio).

## 7. 컨텍스트 분산 (용도/타입 다양화)

같은 검증을 타입별로 전부 복제하지 말고, **테스트마다 다른 타입을 배정**해 부수적으로 타입 차이를 포착한다.
적용 예(특수폴더 sc4): 4e/4g/4l/4r/4m = 레지변경(MODIFY_REGIST), 나머지 = 바로가기(SHORTCUT).
타입 간 차이가 실측으로 발견되면 그때 해당 검증만 양쪽 타입으로 확장한다.

## 8. 적용 예 (2026-07-02, 특수폴더)

| 카드 | 구성 | merge_key |
|---|---|---|
| [수동 확인 필요] 관리자 암호 인증 | sc3f(생성) + sc4m(수정) | `manual_admin_pw_crypto` |
| 원본위치 3000자 오버플로 | sc3s + sc4o (같은 결과일 때) | `path_ovf::원본위치::warn::…` |
| 대상위치 3000자 오버플로 | sc3s + sc4o (같은 결과일 때) | `path_ovf::대상위치::warn::…` |
