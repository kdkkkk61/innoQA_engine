# 시나리오 5: 케이스 검증

> 목적: **저장한 값이 재오픈 시 정확히 유지되는가** — 전체 필드(케이스A) / 필수만(케이스B).
> 핵심은 ON/OFF 전환이 아니라 **입력값 유지 + 빈값 유지** 검증이다.
> 모달이 있는 모든 페이지에 적용. 케이스A와 케이스B는 항상 쌍으로 구현.
>
> **범위**: **정상 입력 조합** 만 검증. 위반 입력(필수 비움 등)은 시나리오 4-3 영역.

---

## 시나리오 4-3과의 차이 (혼동 방지)

| 항목 | 시나리오 5 케이스B | 시나리오 4-3 |
|------|---------------------|---------------|
| 입력 | **필수만 채움** + 선택 비움 | **필수 비움** + 다른 필드는 그대로 |
| 의도 | 정상 흐름 (선택 빈값 유지 검증) | 위반 흐름 (필수 빈값 시 결과 검증) |
| 검증 대상 | **선택 필드** 빈값 유지 | **필수 필드** 실제 저장값 |

→ 텍스트 표현이 비슷해 보일 수 있으나 영역이 명확히 다름. 케이스B는 **정상 최소 입력**.

---

## 시나리오 4-2와의 차이 (되돌리기/비움 전이 — 혼동 방지)

| 항목 | 시나리오 4-2 | 시나리오 5 되돌리기(비움 전이) |
|------|--------------|-------------------------------|
| 입력 | 값 → **다른 값** (대표값 변경) | 값 → **빈값/제거/OFF** (상태 전이) |
| 의도 | 수정이라는 **동작**이 되는가 | 채운 **상태**를 되돌렸을 때 온전히 유지·반영되는가 |
| 실측 예 | 특수폴더 sc4f 설명 변경 = 정상 | 특수폴더 sc5c 설명 비움 = silent 무시(제품 버그, 2026-07-02) |

→ 4-2 가 pass 여도 비움 전이는 별개 입력 클래스 — **비움/제거/OFF 전이는 시나리오 5 소관**
(제어스위트 5b 전체 OFF / 5c 전부 제거와 동일 배치). 5 에서 이슈가 나오는 것은 역할 정상.

---

## 핵심 개념

| 구분 | 설명 |
|------|------|
| **ON/OFF 전환** | modal_form 계열(RansomCruncher 등)의 구현 방식 — 시나리오 5의 일부 표현일 뿐 |
| **케이스A/B** | 시나리오 5의 본질 — **저장 후 모든 필드 값 유지 여부** 확인 |

→ ON/OFF가 없는 list_page 페이지도 케이스A/B로 시나리오 5를 구현해야 한다.
→ "ON/OFF 케이스 해당 없음"이라고 skip 처리하면 안 된다.

---

## ⚠️ 두 가지 함정

### 함정 1: ON/OFF만 구현하는 함정

modal_form 계열(RansomCruncher 등)에서 ON/OFF 전환 패턴으로 시나리오 5를 구현한 경험이
list_page 계열에 잘못 이식되는 경우.

```
잘못된 판단: "이 페이지는 ON/OFF 전환이 없으니 시나리오 5 해당 없음 → skip"
올바른 판단: ON/OFF 전환은 케이스A/B를 표현하는 수단 중 하나일 뿐
            케이스A/B 자체는 모든 페이지에 적용된다
```

**ON/OFF가 없어도 케이스A/B는 항상 구현해야 한다.**

---

### 함정 2: 케이스B를 부실하게 만드는 함정

케이스A(전체 채우기)는 직관적이라 상세하게 구현되지만,
케이스B(필수만 입력)의 "빈값 유지" 검증이 누락되거나 일부만 확인하는 경우.

```
잘못된 케이스B: 필수 필드 로드만 확인, 선택 필드는 건너뜀
올바른 케이스B: 선택 필드 전부 빈값 확인 (단 하나도 빠지면 안 됨)
```

케이스B에서 누락하기 쉬운 항목:
- 선택 텍스트 필드 (설명, 실행경로, SHA2 등)
- **연결 항목 카운트** (프로세스 등록 없음 → 카운트가 정말 0인가)

**케이스B의 빈값 검증 항목 수 ≥ 케이스A의 선택 필드 확인 항목 수** 를 만족해야 한다.

---

## 반드시 커버해야 할 항목

| 케이스 | 내용 | 비고 |
|--------|------|------|
| **케이스A** | 모달의 모든 필드 채우기 → 저장 → 전 필드 재확인 | 연결 항목(프로세스 등) 포함 |
| **케이스B** | 필수 필드만 입력 → 저장 → 선택 필드 빈값 유지 확인 | 연결 항목 0개 유지 포함 |

### 케이스A 재확인 필드 원칙
- 모달에 존재하는 **모든 필드** 확인 (실행경로, 설명, 서명 등 선택 필드 포함)
- 입력값과 로드값이 일치하는지 `==` 비교
- SHA2 등 긴 필드: 값 존재 여부 + 앞 N자 표시
- **연결 항목(프로세스 등)**: 케이스A에서 1개 이상 등록 → 재오픈 시 카운트 유지 확인

### 케이스B 확인 필드 원칙
- 필수 필드: 저장값 로드 확인
- 선택 필드 **전부**: 빈값(`""`) 유지 여부 확인 (하나라도 누락 금지)
- **연결 항목(프로세스 등)**: 케이스B에서 등록 없이 저장 → 카운트 0 유지 확인

---

## 구현 흐름 (페이지별 공통 뼈대)

이 흐름은 방향 제시용이다. 실제 메서드명·변수명은 해당 페이지에 맞게 작성한다.

### 케이스A 흐름

```
1. 사전 정리 (delete_all_auto_items)
2. [AUTO]_sc5_full 항목 생성 — 모든 선택 필드 포함
   - add_item()으로 처리 안 되는 필드는 수정 모달로 보완 후 저장
   - 연결 항목(프로세스 등)이 있는 페이지: 1개 이상 등록
3. 수정 모달 재오픈 → 필드별 저장값 == 입력값 확인
   - 짧은 필드: 값 일치(==) 비교
   - 긴 필드(SHA2 등): 존재 여부 + 앞 일부 표시
   - 연결 항목: 카운트 ≥ 1 확인
4. 모달 닫기
```

### 케이스B 흐름

```
1. [AUTO]_sc5_req 항목 생성 — 필수 필드만, 선택 필드 일절 건드리지 않음
   - 연결 항목(프로세스 등): 등록하지 않음
2. 수정 모달 재오픈 → 선택 필드 전부 빈값("") 확인
   - 목록에서 빠지는 선택 필드가 없어야 함 (함정 2 방지)
   - 연결 항목: 카운트 == 0 확인
3. 모달 닫기
4. 정리 (케이스A/B 항목 모두 삭제)
```

### 계열별 유의사항

| 계열 | 유의사항 |
|------|----------|
| list_page (nPouch 등) | `_make_r` 패턴 사용, 연결 항목 카운트 포함 |
| list_page + 연결 항목 | 케이스A에서 연결 항목 등록 절차 포함 |
| modal_form (RansomCruncher 등) | ON/OFF 프로파일이 케이스A/B 역할을 하기도 함 — 단, 케이스B 빈값 확인이 여전히 필수 |

## YAML 연동

```yaml
# config/scan_hints/{page_id}.yaml
fields:
  # required: true 필드 → 케이스A에서 채우기 + 케이스B에서 로드 확인
  # required: false 필드 → 케이스A에서 채우기 + 케이스B에서 빈값 확인
  - id: execPath
    label: "실행경로"
    required: false
    # 케이스A: 채워서 저장 → 재확인
    # 케이스B: 채우지 않음 → 빈값 유지 확인
```

---

## 주의사항

- **함정 1 방지**: "ON/OFF 케이스 해당 없음"으로 skip 처리 금지 — 케이스A/B는 모든 페이지에 적용
- **함정 2 방지**: 케이스B 선택 필드 빈값 확인 항목을 케이스A 수준으로 맞출 것
- **실행경로는 항상 포함** — 선택 필드라도 케이스A에서 채우고, 케이스B에서 빈값 확인
- `add_item()`에 없는 필드는 수정 모달로 보완 후 저장
- 케이스A/B는 서로 다른 항목 이름 사용 (`[AUTO]_sc5_full`, `[AUTO]_sc5_req` 등)
- 프로세스 등 연결 항목이 있는 페이지: 케이스A에서 최소 1개 등록, 케이스B에서 0개 유지 확인

## 자동 검증 카드 (신규 발견 요소 — `discovered_case`)

시나리오 1 의 `discovered_new` 로 발견된 yaml 미등록 신규 필드는 시나리오 5 영역에도
**자동으로 카드 등록**된다. 단, 케이스 검증의 본질이 "시점별 값 유지" 이므로 다른 시나리오와
달리 **ON/OFF 시점 각각 1장씩 = 신규 필드당 2장의 카드** 등록.

### 동작 (modal_form profile case 흐름에 끼어들기)

1. `verify_created` 직후 (전체 ON 상태 EDIT 모달) — `[전체 ON]` 카드 생성
2. `verify_modified` 직후 (전체 OFF 상태 EDIT 모달) — `[전체 OFF]` 카드 생성

각 시점에 DOM 읽기로 현재 값 캡처. 추가 클릭/입력 동작 없음.

### 카드 라벨 컨벤션

- `label = "[신규] [{case_label}] " + 한국어 라벨`
  - 예: `[신규] [전체 ON] 소프트웨어 인증 사용`
  - 예: `[신규] [전체 OFF] 소프트웨어 인증 사용`
- `detail = "[자동 분류 — yaml 미등록] 타입: {dom_type} / 현재 값: {state}` /
  케이스 검증(전체 ON·전체 OFF) 대상 외 — yaml 등록 시 test_profiles 의 verify_* 에 추가 필요"`
- pattern: `discovered_case`

`현재 값` 표시:
- checkbox/radio: `ON` / `OFF`
- text/number: `'값'` 또는 `(빈값)`

### 검수자 후속 처리 안내

자동 분류 카드 detail 에 명시: **"yaml 등록 시 test_profiles 의 verify_* 에 추가 필요"**.
즉 검수자가 이 카드를 보면:
1. 신규 요소를 정식 케이스 검증 대상으로 편입할지 결정
2. 결정 시 `config/test_profiles/{page_id}.yaml` 의 `verify_created` / `verify_modified` 에
   selector + expected value 추가
3. 다음 실행부터 정식 `profile_verify` 카드로 검증 시작

### case_label

현재 modal_form profile 의 케이스는 `전체 ON` / `전체 OFF` 2개로 고정.
`_scenario5_discovered_cards(case_label=...)` 가 그 라벨을 `[{case_label}]` 형식으로 prefix 부착.

### 회귀 안전

- EDIT 모달 열린 상태(modal_already_open=True) 에서만 실행.
- DOM 읽기만 — 추가 클릭/입력 동작 없음.
- 자동 분류 결과는 모두 pass (검증 목적 = 표시).

### list_page 계열 (미지원)

현재 `discovered_case` 는 modal_form profile case 흐름에서만 동작 (test_profiles yaml 기반).
list_page 계열은 케이스A/B 가 다른 흐름으로 구현되므로 자동 분류 미지원.

→ 자동 분류 메커니즘 전체 흐름은 `test_scenario_standard.md` "자동 분류 메커니즘 (B-1 시리즈)" 참조.
