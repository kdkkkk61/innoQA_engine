## 2. 확장 방향 (두 개의 축)

### 축 A — 멀티 제품 지원 (수평 확장)

> 동일한 테스트 유형(Manager UI 스캔)을 다른 제품에도 적용

```
현재: 랜섬크런처
확장: 랜섬크런처 / 이노마크 / 시큐어존 / ...
```

**전제조건 (구현 전 반드시 확인 필요)**

| 확인 항목 | 방법 | 상태 |
|-----------|------|------|
| 이노마크 Manager UI 프레임워크 | Chrome MCP로 실제 페이지 접속 후 확인 | ⬜ 미확인 |
| 시큐어존 Manager UI 프레임워크 | Chrome MCP로 실제 페이지 접속 후 확인 | ⬜ 미확인 |
| 제품 간 공통 UI 패턴 비율 | 두 제품 접속 후 selector 겹침 분석 | ⬜ 미확인 |
| 각 제품 로그인 방식 동일 여부 | 로그인 페이지 selector 확인 | ⬜ 미확인 |

**아키텍처 방향 (확인 후 결정)**

| 시나리오 | 구조 | 적합한 경우 |
|----------|------|-------------|
| UI 프레임워크 동일 | 공통 BasePage 재사용, scan_hints YAML만 추가 | AngularJS 공통 |
| UI 프레임워크 다름 | 제품별 BasePage 서브클래스 또는 어댑터 레이어 추가 | 프레임워크 상이 |

---

### 축 B — 기능 검증 테스트 (수직 확장)

> Manager UI에서 정책 생성 → VM 에이전트에서 실제 동작 확인

```
현재: Manager UI 스캔만 (UI가 올바른지)
확장: 정책 생성 → VM 적용 → 에이전트 동작 검증 (실제 기능이 동작하는지)
```

**전제조건 (구현 전 반드시 결정 필요)**

| 결정 항목 | 선택지 | 현재 상태 |
|-----------|--------|-----------|
| VM 연동 방식 | Playwright(UI 자동화) / API+로그 / SSH+파일시스템 | ⬜ 미결정 |
| 테스트 대상 VM 위치 | QA Tool 실행 PC와 동일 / 별도 VM | ⬜ 미결정 |
| 검증 기준 | 차단 팝업 UI 확인 / 로그 파일 파싱 / API 응답 | ⬜ 미결정 |
| 테스트 시나리오 정의 | 어떤 정책을 만들고 어떤 행위를 시뮬레이션할지 | ⬜ 미결정 |

**기능 검증 흐름 (예시 — 랜섬크런처 기준)**

```
1. Manager에서 [AUTO] 탐지 정책 생성
   └─ 탐지등급: 높음, 롤백: ON
2. VM 에이전트에 정책 동기화 대기 (폴링)
3. 테스트 행위 실행 (파일 암호화 시뮬레이션)
4. 에이전트 반응 확인
   └─ 차단 팝업 / 롤백 동작 / 로그 기록 여부
5. 결과 리포트
6. 테스트 정책 삭제
```

## 3. 제안 개발 순서 (단계별)

### Phase 1 — 전제조건 리서치 (현재 단계)

```
□ 이노마크 Manager 페이지 Chrome MCP 분석
  - AngularJS 여부 확인
  - 로그인 selector 확인
  - 주요 페이지 URL 패턴 확인

□ 시큐어존 Manager 페이지 Chrome MCP 분석 (동일)

□ VM 기능 테스트 방식 결정
  - 연동 프로토콜 선택
  - 테스트 시나리오 목록 작성
```

### Phase 2 — 멀티 제품 아키텍처 (축 A, 리서치 완료 후)

```
□ 제품 레지스트리 구조 설계
  config/products/*.yaml
    ├─ ransom_cruncher.yaml
    ├─ inno_mark.yaml
    └─ secure_zone.yaml

□ 제품별 scan_hints 분리
  config/scan_hints/
    ├─ ransom_cruncher/
    │   ├─ ransom_detect_policy.yaml
    │   └─ ...
    ├─ inno_mark/
    └─ secure_zone/

□ UI 프레임워크 차이에 따른 BasePage 확장 (필요 시)

□ 제품 선택 화면 → 선택된 제품 scan_hints 자동 로드
```

### Phase 3 — VM 기능 검증 테스트 (축 B, 방식 결정 후)

```
□ VM 연동 모듈 구현 (vm_connector.py)
□ 테스트 시나리오 YAML 정의
□ 기능 검증 runner 구현
□ UI에 "기능 검증" 테스트 타입 추가
```

## 4. 독립성 원칙

두 축은 **서로 독립적으로 진행 가능**하다.

- 축 A (멀티 제품): 기존 Manager UI 스캔 구조를 그대로 활용 → 리스크 낮음
- 축 B (VM 검증): 완전히 새로운 테스트 패러다임 → 별도 설계 필요, 리스크 높음
- 두 축을 섞으면 복잡도가 급격히 증가 → **Phase 2 완료 후 Phase 3 시작 권장**

## 6. 즉시 할 수 있는 것 (리서치 단계)

리서치가 완료되기 전에도 바로 시작 가능한 작업:

```
1. Chrome MCP로 이노마크 Manager 페이지 분석
   → 결과에 따라 Phase 2 설계 방향 즉시 결정 가능

2. 현재 config/scan_hints/ 구조를 제품별 폴더로 마이그레이션 준비
   → 기존 랜섬크런처 기능에 영향 없는 파일 구조 변경

3. config/products/ 레지스트리 YAML 스펙 초안 작성
   → 제품 추가가 YAML 파일 하나 추가로 끝나는 구조 설계
```
